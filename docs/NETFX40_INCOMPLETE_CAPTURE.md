# Original Microsoft .NET 4.0 incomplete Wine stderr observation

The authentic 4.0 Apple Silicon Wine run [43742668054](https://github.com/ABCPeter123/Mac-Compatible-Solidworks/actions/runs/43742668054) ended with original MSI 1603, no Microsoft native CLR, and a still-active observed installer child. The bounded `WINEDEBUG` pipe drain did not reach EOF after the 5-second reader join, so the collector correctly reported `TRUNCATED` and `READER_UNFINISHED`. Since the previous private action store required an entirely finished pipe, no target action was passed to the already-compiled read-only MSI Binary import inspector. `ACTION_NOT_CAPTURED` did not mean the MSI had no custom action.

This change permits only a **private action candidate** when a complete allowlisted Wine `err:msi:execute_script` action marker is present in the bounded memory snapshot and the only incompleteness is an inherited, still-open stderr pipe (`READER_UNFINISHED`). It continues to reject line/byte overflow, launcher timeout, missing or non-fatal setup status and known script-2 rollback-only actions. Script 0 install-phase actions take priority over unscoped markers. A still-running child does not count as a completed installer, and the trace remains `TRUNCATED` in public evidence. No missing lines are inferred.

The target action identifier is stored once in a mode-0600 temporary file only within the marked disposable Wine prefix. It is consumed and deleted before read-only MSI table queries. The helper uses the original signed Microsoft `/x` extraction and does not copy proprietary DLL bytes into repository artifacts. A positive PE import census is architectural evidence, **not** a proven root cause, installed .NET CLR or SOLIDWORKS compatibility. The next phase must establish the install-script provenance and reproduce a particular Wine API deviation before patching Wine.
